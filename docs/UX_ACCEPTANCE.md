# UX acceptance brief

This brief defines observable acceptance for the locally hosted, single-player Storyteller MVP. It follows the committed `IMPLEMENTATION_PLAN.md`; it does not define new game mechanics. A screen is accepted when the player can understand what is happening, choose what to do, and recover without losing or duplicating campaign state.

The owner's priority is a fun, engaging, quick-paced, consistent, lifelike campaign. Cost is never the optimization target; usage and byte counts are diagnostics only and cannot justify dropping relevant facts, flattening character voices, or slowing play with unnecessary retries.

## MVP exit and next product priority

### V1 P0 context-size resilience

The configured 128,000 serialized-byte value is a generous prompt-shaping signal, not a prompt-size ceiling, model context limit, cost objective, or ChatGPT-plan usage limit. When the complete assembled request fits, preserve it in full; do not remove records or detail because a fixed category count was reached. Only when the whole request exceeds the target should the compiler rank facts for the current action and compact unrelated or redundant history and reference prose. Keep explicitly named characters, places, items, resources, active duties, and current-scene anchors in view. If the best relevant request still exceeds the target, send it instead of stripping useful canon to satisfy an arbitrary byte count. Gameplay requests do not carry an exact local body veto; the provider reports its actual model limit. Do not discard or rewrite canonical source records to fit a request.

The scene-focused retrieval packet is a recovery path for a provider-reported context-length rejection, not the normal response to crossing Storyteller's target. It is sent without a local serialized-byte cap, including its lookup continuation. A provider context-length rejection automatically retries once with the packet in the same claimed turn. If the provider rejects that packet too, keep the saved action and canon unchanged, explain that the GM could not answer this turn, and leave the turn safely retryable. This avoids inventing an app-level hard ceiling; it cannot make arbitrarily large active context fit the provider's real model window.

The test evidence covers the behavioral contract: even a tiny configured target sends the useful request rather than a retrieval-only packet; an above-target relevant request can reach the provider without a local body rejection; and provider context rejection retries that same saved action automatically with a scene packet. If both automatic requests are rejected, the first manual retry preserves the relevance-ranked campaign context and any useful facts above the former 48 KB target, while skipping optional MCP companions; it does not squeeze history to four events or clip prompt content solely to meet a number. A further retry may use the minimal scene packet. Public diagnostics must not reveal private prompt contents or lookup arguments. Serialized bytes are request diagnostics, not token counts or cost estimates. This uses an app-defined local function, not hosted MCP: the ChatGPT-plan preview excludes hosted MCP/connectors and `previous_response_id`, so each request carries its needed context. Function definitions, returned facts, and extra round trips still affect context and latency; compare recall, privacy, provenance, continuity, and latency before claiming retrieval is better.

The context-growth audits found unbounded world-state maps, tracked-resource rows, present-character/place details, and objective backlogs. Under actual size pressure they receive action-ranked projections with stable public date/time/weather/location anchors and explicit completeness flags; the database remains authoritative, and omitted values or rows are not treated as absent. If the full request fits, these projections must not truncate details. High-growth synthetic coverage includes a 107-character cast, 94 places, and 122 objectives, plus a near-cap description case with 48 characters, 64 places, and 96 objectives. At the time it was measured against the earlier 64,000-byte target, the latter compiled to 42,050 bytes while preserving the selected NPC's public/private ledger evidence, current scene, and forty-minute route. A separate Play integration regression carries 36 ordinary turns through three successive sessions and records the actual serialized sizes; this representative campaign remains under the compaction target. Above-target relevant requests and provider-rejection recovery have separate deterministic coverage. These tests do not establish arbitrary campaign-size support, generated-story continuity, or provider acceptance. Continue expanding fixtures for multilingual implicit references and longer multi-session campaigns.

The MVP gate is functional QA: the campaign/session loop, configured local GM connection, actions and questions, time passage, player rolls, tracked state/resources, durable cross-session continuity, relevant context assembly and recovery, and recoverable failures must work on separate fictional data. Passing this gate means the core product functions; it does not claim that generated stories are compelling or meet the V1 story-quality bar.

After the functional gate, V1's P0 is story quality: engaging scenes with flexible pacing, clear GM ownership of external facts, distinctive characters, smooth handoffs, continuity, and acceptable latency. UI glitches that disrupt play remain active V1 work. Open-source clone/run documentation and a secret/private-data audit follow when the owner considers play polished enough. Version 1.0 ships only after the story-quality bar is met; passing MVP QA alone is not a 1.0 release. See the V1 scenario review and measures in `IMPLEMENTATION_PLAN.md`.

## Defining promise: a consistent world, with relevant context

Storyteller's defining promise is that the campaign stays coherent because the application maintains structured canon, not because the GM model is expected to remember every detail in a long transcript. Persisted characters, places, connections, presence, inventory, and campaign resources are authoritative; narration is accepted only when its proposed changes agree with that canon. The full campaign history remains durable, while each GM request receives only a compact, relevant projection so consistency does not require sending the whole campaign every turn.

The library's primary path stays focused on creating, opening, and resuming stories. Both sections explain that backup files contain private GM context.
- Saving campaign edits shows a clear inline success confirmation or save-blocking error beside the save controls. A validation error keeps the full voice draft visible and commits no partial notes; after a successful voice edit, reopening the editor shows the saved values and future GM context receives them.
- From the existing campaign editor, the owner can add a GM-controlled character with a required name, optional player-visible facts, GM-only notes, and the standard five GM-only voice-guidance fields. The add-character panel starts collapsed and opens when its draft has content. Its optional current-place selector contains only existing public canonical places; leaving it blank keeps the new character unplaced and does not infer presence. Saving creates no story event and does not advance the world clock. New-character creation is included in the durable authoring correction transaction; notes and voice guidance mark that correction private and remain absent from public correction history and projections. Malformed places and over-limit voice notes are rejected without partial campaign or character writes, and the draft stays available after the error. Creation waits until any in-progress turn finishes so an older GM response cannot treat the new speaker as present.

## Create campaign

- A guided flow collects the campaign title, story premise, setting, tone, narration language, player character details, optional GM-controlled characters, starting location/date/weather, and any campaign-specific mechanics. It makes required versus optional inputs clear without inventing rules or requiring unsupported character fields.
- GM-character setup can optionally record each character's starting place as canonical presence. Use the campaign's exact opening-location name to place someone with the player; a different name creates a separate public place without inventing a route. A blank field leaves the character's origin unknown, and the game must not silently place every character with the player.
- Setup is grouped into four compact steps—story, player character, starting scene, and optional people/details—then a review before creation. Back and forward navigation preserve entered values, and validation returns to the relevant step. Keep one form flow, avoid losing work during the transition, and do not hide configured optional rows.
- Opening-scene validation errors for the starting location, date, time, or weather return to the Opening scene step with the entered draft intact; they must not strand the player on the final optional-details step.
- Voice guidance belongs in each character setup and edit section. Show a concise example of audible choices (measured pauses, short phrases, careful word choice) and explain that the profile guides GM delivery; discourage phonetic spelling and stereotyped accents. Edits to all five fields must survive save and reload, and reach later GM context for that speaker without rewriting earlier story entries. If another campaign field rejects the save, show clear failure feedback and preserve the voice draft. In play, keep accent/dialect, vocabulary, cadence, quirks, and mannerisms tied to that speaker; use natural speech rather than phonetic caricature, catchphrases, or repeated mannerisms. A request-context regression verifies persistence and per-speaker delivery; live output distinctness still needs human play review.
- Optional player facts, starting inventory, GM characters, and campaign panels are explicitly labeled optional. They begin collapsed when empty, then open when a row is added so the main setup path stays easy to scan without hiding configured content.
- The player can review the assembled setup before creating the campaign. Editing or returning between steps preserves entered content; validation identifies the affected field and explains how to fix it.
- Successful creation opens the new campaign in a ready-to-play state. The chosen narration language is stored separately from the interface locale.
- Exact wizard step order, field-by-field validation, and which setup fields are required remain design choices unless specified by product decisions.

## Play screen and player agency

- The play screen presents a readable, chronological timeline that distinguishes player input, GM narration, speaker-attributed NPC dialogue, public remote messages, relevant GM-controlled character activity, and rolls. A remote message has a visibly distinct style and sender label, and its stored event type is not `npc_dialogue`. New completed turns appear without a full-page reload. On a fresh session open, the independent story viewport lands on the newest visible entry after initial layout settles; while reading older story, updates and prepended history preserve the reader's position. The composer and side panels remain outside that scroll viewport. The initial recent window is bounded; a clear action loads preceding campaign history in chronological order until the earliest event is reached.
- The play surface foregrounds the character's immediate situation and campaign-relevant facts. Interface preferences such as English/Spanish/French and the connected-account GM model belong in Settings, not beside the story as a primary action. The model choice must be drawn from the connected account's available catalog, persist locally, default to Automatic, and apply to new turn resolutions; controls stay off the play board. Account settings state that Storyteller requests low reasoning effort for supported models and leaves other models at their default. In the story, show canonical game date/time at the first event of each turn, then repeat it within that turn only when the clock changes. Keep those markers correct across sessions and when older pages load; never show real-world timestamps. Avoid other repeated labels, setup/admin details, and state already clear from the board; keep a direct path to deeper reference when the player wants it.
- Looking around, tasting, or inspecting something reports what the character can perceive from their current public vantage before asking what the character makes of it. Match sensory detail to the action: use enough salient, supported evidence to answer a focused question and help the player choose what to do; there is no fixed detail-count ceiling. In sparse scenes, add any relevant ordinary, non-actionable sensory texture the setting and action warrant, without repetition or padding. Observation retrieval must follow the same vantage boundary across supported language forms, including Rioplatense voseo commands such as “mirá” and “probá.” English, Spanish, and French tasting verbs must route to vantage-scoped observation retrieval, not broad keyword search. In a tasting, the GM owns the wine's sensory profile and describes it before inviting the player's reaction; never ask “What does it taste like?” or otherwise ask the player to author external sensory facts. Keep the player's character in control of their interpretation, speech, and next action. These answers do not replay the scene, repeat the situation panel, or echo the previous answer. Ambient texture stays source-free and cannot create a person, item, exit/route, hazard, clue, service, or other actionable fact; those require accepted canon, with accepted presence for a person. A direct answer can end naturally; suggest a next step only when the observation creates a concrete, useful opening, never with a generic invitation. If an action depends on an untracked feature, the GM states uncertainty or asks. Ask GM leaves fictional time and canonical state unchanged.
- Small scene cues help ground time and conditions in the imagined world (for example, a moon behind clouds with mist at midnight). Time and weather cues are independent: show the known sun/moon when weather is unknown, and recognized cloud/mist/rain/snow when time is unknown; use a fully neutral cue only when neither is recognized. Story entries arrive gently in the already-paced sequence, and a changed panel value gets a brief cue in place. Keep words authoritative and readable; imagery and motion support the game instead of demanding attention.
- NPC speech is visually attributed to its speaker. Visible activity communicates what relevant NPCs do; it does not reveal private facts, hidden motives, offstage events, or other GM-only state.
- A compact header shows current player-visible world state, including location and in-world date/time and weather where available. Configured campaign panels show their labelled, typed, unit-aware visible fields; the vineyard may use cash, wine inventory, and vine inventory. Panels must not expose private values.
- Resource labels, units, numbers, and long or multiline text stay readable in both the play sidebar and campaign detail. Preserve line breaks inside the value only; do not expose template indentation or add large gaps around receipts and correction links. Keep GM-private values absent.
- Public tracked resources with a saved change can expand a collapsed “Last changed” detail beside the value. It shows the accepted before/after, public reason, and in-world time. Private panel values and private reasons never appear in that detail; no state-change receipt is added to the story timeline.
- In a resource-focused campaign, an accepted sale can update both cash and stock through configured panels. The player sees each current value and its receipt beside the relevant ledger, with no system chat entry. After starting a later session, the board and next GM request use the updated balances. This exercise must not depend on vineyard-specific code.
- Public place and character changes can expand a collapsed “Last changed” detail on their relevant board cards. Show only accepted public state: a place's creation, a character's visible fact update, or a character's move between known public places, with before/after values, an available safe reason, and in-world time. Exclude GM-private places, presence, facts, and reasons; keep these receipts in panels rather than chat.
- Each date, time, and weather fact has one canonical value across the GM's hidden context, the compact header, and the scene board. Legacy aliases and conflicting persisted values must not create duplicate or contradictory facts in play.
- A player can find a concise character board during the scene: current place first, the public places reachable by one canonical route with their in-world travel time, the latest public GM narration as the immediate situation, character details they know, current companions' visible activity, and owned inventory/resources. Names and current public activity of canonically co-present companions appear directly on the scene card without opening place lore; show at most three there and keep any larger cast behind a collapsed continuation. Nearby-place display must filter both private routes and private destination places. The latest narration updates as play continues and never includes GM-private context. This should answer “where am I, what is happening, who is with me, what do I carry or control?” without reading the entire timeline first.
- Keep the player character's name and public description visible in a compact “Your character” card beside the scene and inventory. Show up to three stable public character details at a glance and disclose any additional details only when expanded. Changes cue that card in place; GM-private facts never enter it. A mobile section link makes the card directly reachable without scrolling through the timeline.
- The campaign premise remains available as an expandable reference during play, without leaving the session or repeating it in the event timeline.
- The Plus OAuth game-master route supports streamed text but not generated scene images. Do not add paid API image calls implicitly; scene illustration remains an open integration for a local image generator or player-provided campaign art.
- Campaigns can model distinct carried items and consumables with stable identity, owner, quantity, unit, and any campaign-relevant safe details. Resource ledgers also support non-item values such as vineyard cash, wine stock, and vines. The same interaction works for different campaign genres without hardcoded vineyard or dungeon rules.
- A text composer lets the player submit an action or speech. Pending submission prevents accidental duplicates and makes the submitted text and resulting turn status understandable.
- Contextual play nudges include looking around, asking a direct question, waiting at the current place, and explicitly letting time pass. Let time pass includes a **Pass a few days** nudge that stops at the next meaningful player decision; the player can still request a custom duration in the composer. Time passage preserves a duration the player stated, including multiple days, and may advance world or NPC activity; it never chooses or narrates the player's actions, speech, thoughts, movement, or rolls. The structured clock contract in the defining-promise acceptance checks governs elapsed minutes; the calendar remains the campaign's free-form label. Accepted date/time and exact elapsed clock survive a later session and reach its next GM request together with the earlier passage and narration in campaign history.
- A newly submitted player action stays visibly in the story while the GM works, including after reconnect; when the canonical event arrives, it replaces the pending preview without duplication. Once the first streamed text arrives, the wait status gently advances to show the GM has begun composing. Keep all generated text hidden until the complete response passes validation and its canonical event is committed; failed or incomplete streams never imply that an answer is ready. New GM, NPC, and world beats reveal in a paced sequence with a clear show-all control. Initial history is not replayed, and loading older history preserves the reader's position.
- The story reads like a tabletop conversation: player actions, natural GM narration, direct character dialogue, and relevant roll prompts. A completed response feels like one coherent GM turn, not four or five abrupt, disjointed messages. When a character has related things to say, combine them into one concise utterance and speech bubble; avoid filler and repeated lines. Do not add system-style chat entries for memory, inventory, location, resources, objective status, or character-record mutations. Those changes appear in their corresponding panels and receive a brief, restrained animation; status-only changes such as an objective moving from Open to Completed still trigger the cue. The durable audit record remains available to the application without cluttering the conversation.
- Scene tempo adapts to intent and scope. Direct questions, consequential choices, and tense instants stay close and leave a natural opening for the player's reply. An in-character exchange reaches its natural handoff; the GM does not stop just because one NPC has acted or spoken when grounded reactions or dialogue still complete the scene beat. Clearly ongoing work or an explicit interval resolves in one flowing scene summary at the requested scale, including meaningful progress and relevant reactions by characters who are present; routine micro-actions are not serialized into a prompt after every step. Sensory facts are established by the GM before asking for the player's interpretation. On focused inspection of an established target, the GM describes what the action reveals from the character's vantage without asking the player to invent observations; unsupported history or cause stays uncertain. If the player's scope is unclear, the GM stops after the immediate consequence. Human review compares paired routine, focused-action, and ensemble-scene tasks and records player prompts needed to reach the next real decision, scope/time advancement, agency and continuity errors, and response latency. Fake-provider tests cover prompt guidance and state boundaries, not live prose quality.
- New characters are introduced through the GM's scene narration and their own dialogue. Their structured facts update the character panel without “new character” notices or stat dumps. Date/weather changes are described naturally while the canonical world bar updates and briefly signals the changed value.
- On roomy desktop viewports, the play board fills the window: the story is the only overflowing vertical reading surface while world facts, campaign resources, current scene, inventory, and composer remain in place. Keep the essential world rail visible; clamp its immediate-situation preview while the full narration remains in story history. Narrow or short viewports keep normal document scrolling so controls remain reachable. Loading earlier story preserves the visible event anchor.
- If campaign artwork is supported, reveal each image beside its story beat at the same readable pace and let the player skip ahead. The current Plus OAuth route cannot generate images; a local generator or player-provided campaign art must be selected before paced image cards can be implemented without adding API billing.
- The board exposes active public campaign memory as expandable notes with a concise add/edit/retract path; it is clearly separated from private GM context. Saving a public memory note records its reason and audit trail without a system-style timeline message or in-world time change. Durable private GM context remains hidden from every player-facing projection, and public resolutions/retractions remain traceable without exposing private reasoning.
- The GM responds to player choices with natural consequences, preserves established facts, and returns control to the player. The UI never writes the player's actions, speech, thoughts, or choices on their behalf. It does not present a proposed state change as canonical before the application accepts it.
- Location, character presence, inventory ownership, and resource quantities are canonical persisted state. Narration alone cannot change them: accepted state deltas reference stable records, are validated, committed once with their turn, and appear in a traceable history. If a turn records multiple player movements, the final canonical place and world location agree in the player board and later GM context. Numeric campaign balances use signed deltas applied against the locked current value; text/status/date fields use typed set operations. Each resource history entry shows the field, before and after values, operation, unit, and grounded reason. A read-only account review creates no balance change.
- Place connections and travel durations, plus character location and presence, constrain who can plausibly appear in a scene. A character away from the current place does not enter the conversation for incidental dialogue unless accepted movement or an established communication path explains their presence. If the player's canonical place is missing or unknown, public NPC dialogue and activity are rejected until the scene is established; unknown location is not shared presence. Remote communication remains a separately validated event and does not imply in-scene presence.
- Establish a public sender-to-player communication path only through an explicit accepted path operation tied to the known NPC's public in-scene dialogue; its cited basis text must exactly match that line, and the line must plainly name the usable endpoint so the player can use it without guessing. `public_changes` and its case/separator-normalized aliases cannot seed or edit the path ledger. Each accepted establishment or deactivation has a public before/after `state_change` audit record in the same transaction, outside the story timeline. A delivery references the previously saved active path ID and matching sender. Missing, inactive, and sender-mismatched paths are rejected atomically. GM context includes at most 12 active paths, with query-matched routes and then recent routes ranked first. A remote delivery alone does not move the NPC or change world time or routes. Ordinary off-scene dialogue/activity presence validation remains unchanged. Path canon round-trips in campaign backup state, and older backups without a path ledger remain importable.
- Long campaigns retain separate public and GM-private continuity summaries. A bounded recent-event window keeps each GM request practical, while older events remain in durable storage and are available to the player through cursor-paginated campaign history. Pages use immutable event sequences, appear exactly once in chronological order, and remain loaded during live updates. Summaries support retrieval but never replace the authoritative item, location, character, and resource records. Private continuity must never appear in player projections.
- Each GM request uses a small, bounded, relevance-ranked projection of canonical facts and retrieved history rather than the full campaign transcript or a repeated dump of world state. Keep exact canonical state in the database; the model's request history is not durable campaign memory. Ordinary campaign growth must not strand a turn at the local size preflight: compact redundant narrative, retrieve only relevant older facts, and retain the current scene essentials without asking the player to hand-edit notes. Test normal through adversarial synthetic growth in English, Spanish, and French; verify relevant canon arrives, unrelated history is omitted, and serialized bytes are distinct from provider token usage. If even essential context cannot fit, preserve source canon and the saved move, explain the oversized category, provide an app-assisted review/curation path, and allow safe retry; never silently drop canon or ask the GM to guess. Evaluate supported app-handled, read-only function tools only by measuring total request/result size, added round trips and latency, authorization, and continuity. Hosted MCP/connectors and HTTP `previous_response_id` are unsupported in the current ChatGPT-plan preview. Keep diagnostics private-text-free.
- Narrow layouts keep the timeline, composer, die when relevant, world header, and access to campaign panels usable without horizontal page overflow. A compact in-page navigation provides a direct jump to the active turn composer, campaign story, combined current-scene/place card, and inventory, plus objectives and tracked resources when those public sections have content. World date, time, weather, and location appear once in the compact header; the scene card gives the place, surroundings, and people present. The exact panel arrangement remains open. Dedicated keyboard, screen-reader, and formal contrast review is V1 work.

## Player-click D20 flow

- If an uncertain, consequential player action needs a roll, the timeline states what is being tested and the difficulty or target before asking for the player's roll. Ordinary actions do not trigger a roll merely to add activity.
- The player initiates the roll with an explicit D20 click. The interface clearly indicates when a roll is awaited, accepted, and resolved; the recorded result is visible in the turn history. The server-generated result is applied exactly once.
- The GM does not silently roll for a player-controlled character. The current MVP lets the player initiate their own D20 result; add a distinct, auditable GM roll only if a campaign's rules require it.
- The exact dice presentation, animation, and any campaign-specific interpretation of targets remain open choices; the interface must not imply mechanics that the campaign has not defined.

## Progress, failure, and reconnect

- While a GM response is in progress, show a clear pending/progress state and keep the player from submitting a duplicate action. Do not imply that a turn is complete before the response is validated and committed.
- If an owned active turn is still resolving after 15 seconds, add a calm localized reassurance in the progress card that the turn is saved and the complete checked GM response will appear when ready. Keep this out of the story timeline and completion announcement. Do not stream unvalidated GM text, promise an ETA, or show the note after the attempt completes, is replaced, or belongs to another session/worker.
- A slow but actively streaming GM response remains the same saved turn across reconnects and never starts a parallel retry. Give response-stream reads a substantially longer idle grace than OAuth/catalog requests, and renew the resolution lease from stream activity with attempt fencing. If the stream goes idle past its receive timeout, fail that same turn recoverably; do not append partial text or apply canon.
- If a submitted action arrives just after another turn became active, or a ChatGPT plan pause raced with submission, keep the unsaved text in the composer and explain why it was not accepted. Do not create a second turn or send the preserved draft automatically when the earlier turn completes or requests resume; the player chooses when to send it.
- On timeout, invalid response, or other recoverable failure, explain that resolution did not complete and preserve the prior canonical state. Retry transient failures automatically before presenting a failure state; a one-fast-retry cap that leaves the player to click through ordinary hiccups is unacceptable. Keep the exact saved action visible throughout. For safely repairable proposal-validation failures, give the GM the specific failed rule and allow up to four guided corrections on that same turn after the original proposal. If the same category returns an identical rejected response once, send a stronger instruction to change it; stop only if the identical response returns again. A changed response continues through strict validation. No partial narration, action, roll, event, or canon change may leak from a rejected proposal, and one accepted result commits once. If recovery is exhausted, keep the action available for a calm same-turn retry without asking the player to retype or recreate it. For a malformed or rejected GM reply, make clear that no part of that reply was added to the story or state; never expose raw model output or private prompt context. If the player already rolled, state that the saved result will be reused. Retrying does not duplicate the action, event, roll, or state change. Never automatically resend while usage is paused, credentials need repair, or the request needs local context correction; explain the specific player action needed instead.
- Exceeding Storyteller's local compaction target never by itself blocks a turn or asks the player to edit campaign data. Send the best action-relevant request and let the provider report its actual context-window limit. If the provider rejects it, retry the same saved action automatically with the compact scene packet; only a repeated provider rejection may surface a recoverable failure. Neither recovery path rewrites canon, drops the player action, or asks the player to curate notes as routine maintenance.
- Public place, route, and objective correction flows remain available from their campaign boards as intentional canon-editing tools. They must not be presented as required workarounds for Storyteller's local byte target. Saving a correction retains existing audit, privacy, continuity, and backup guarantees.
- If a turn is waiting for a player roll, a refresh or reconnect restores that same pending turn and roll request. If a turn completed, reconnect restores the completed timeline and current state. The player should not have to infer whether an action was lost or applied twice.
- When account usage prevents a GM request, show one clear account-wide pause with a link to usage settings and an explicit Resume requests action. This is the only visible explanation of the account limit. Keep the failed turn calm and focused on the preserved action or opening scene; show that same action in the story and keep its Retry this turn control in place but disabled until the player resumes requests. Remove secondary pause warnings from the composer and avoid repeating the limit in status announcements. Resuming only clears the pause; it must not call the provider. After resume, enable retry for the same saved turn, preserve any D20 result and canonical state, and wait for the player to retry explicitly. Do not imply a specific reset time, fictionalize the limit as game energy, or silently switch to paid API usage. Other campaigns may still attempt requests against the shared plan allowance.

## Accessibility (V1 — deferred)

- All actions, including form navigation, campaign/session selection, turn submission, and the D20 click, are keyboard operable with a visible focus indicator. Focus moves predictably after navigation, validation errors, and turn updates.

- New story entries are exposed through a polite, additions-only live region so assistive technology can announce appended events without rereading the full campaign timeline.
- A single, always-mounted polite status region announces saved/reconnecting turns, active resolution, the requested player roll, a recorded result during after-roll resolution, failure/retry, and completion. Completion is announced only after the current connection observes a turn leave the open state; reopening an already completed session does not present old history as a new completion. - Text and controls remain readable at narrow viewport sizes and at increased text zoom. ## QA boundaries

- **Manual gameplay QA:** Exercise the end-to-end experience only in independently authored fictional QA campaigns, such as the Quiet Observatory or another clean fictional setting. Cover campaign creation/switching, multiple sessions and resume, narration/dialogue/activity, a player-click roll, visible panel updates, narrow-screen use, and recovery from a pending or failed turn. Preserve the owner's Vineyard source unchanged; never access, request, export, summarize, continue, import, or test against it or any comparison copy. Use only campaign-independent pacing and tone preferences already captured in project documentation; do not copy campaign data into QA.
- **Automated tests:** Use a separate test database, isolated fixtures, a fake GM provider, and a fixed roll source. Assert observable behavior and durable state for campaign isolation, session continuity, turn statuses/idempotency, visibility, D20 flow, locale changes, failure/reconnect recovery, and loading multi-page campaign history without duplicates or losing loaded pages during refresh. Normal automated tests make no live AI calls. Keep the opt-in live-provider smoke check separate from the default suite.
- **Story quality review:** Human-review scenario fixtures for natural consequences, restrained escalation, consistent facts, independent NPC agency, and preservation of player agency. Do not use exact-prose snapshots as the quality bar.
- **Continuity review:** Across multiple sessions, test no unsupported item gain/loss, no accidental duplicate or wrong-owner transfer, no uncommitted location change, and no NPC appearing in an unestablished place. Confirm private facts are present in the GM's prompt and absent from every player-visible projection.
- **Product benchmark:** Compare the player board, inventory model, location/context navigation, secrets, and campaign memory against AI-native tools and system-agnostic campaign managers. Record what is public product documentation, what was hands-on tested, and what is a Storyteller design decision. Use the comparison to improve core tasks, not to chase feature count. The initial public-source and isolated QA review is in [`docs/PRODUCT_BENCHMARK.md`](PRODUCT_BENCHMARK.md); it is a qualitative baseline, not a completed comparative test.
- **Interaction principles:** Apply purpose, player agency, responsibility, familiar mental models, clear feedback, responsive flexibility, simplicity, craft, and delight. Make accepted changes understandable and reversible where safe; keep settings and state-management details close to the content they affect.

## Named off-scene history retrieval

- In a noisy, multi-session campaign, when the player names an away character and asks whether they can join the current scene (for example, “Could Marisol join us here for the pressing?”), retrieve older history that grounds that character's canonical location or duty without requiring the player to repeat the route, distance, or assignment. Keep the latest 12 story events and canonical place, duty, and route in context; omit same-place/topic history that does not mention the named character; record request bytes for diagnostics; the soft target never blocks provider submission. Queries without an explicitly named away character continue using the existing bounded scene-anchor scoring; this focused cue is not general semantic search.
