## Implemented

- Reviewed campaign setup seeds stable player-owned inventory entries, public world details, GM characters, typed campaign panels, and up to 50 optional player-visible player-character label/value details. Those facts persist with the existing character description and appear in the player projection, board, and GM context; labels/values are bounded and duplicate labels are rejected without adding fixed RPG stats.
- GM proposals can add or revise flexible public facts on the player's character, with a concise action-grounded reason. Validation rejects GM-private player writes, missing reasons, unknown character IDs, and core identity/description changes; accepted patches preserve unrelated facts and apply atomically. The public audit event and timeline show only the fact patch and reason, and updated facts reach the board and later-session GM context. GM-controlled characters keep their existing public/private update behavior.
- GM proposals can introduce a new GM-controlled character mid-play with a stable speaker ID and separate public/private facts. The new character can speak, act, receive items, move, and be updated in the same proposal. Validation rejects duplicate IDs, the reserved player ID, and unknown or invalid places before commit; creation, public/private audit entries, activity, inventory, and presence commit atomically. Public introduction events and projections show only the name, visible facts, and public presence, while both fact scopes and hidden locations remain in later GM context across sessions. This uses the existing character and place tables; no migration is needed.
- The GM receives canonical public and private inventories. Validated add, whole- or partial-stack transfer, consume, and properties-only update operations commit atomically with timeline events; generic state changes cannot edit or replace inventory. Property updates deep-merge nested maps and preserve unrelated values without changing stable IDs or other item fields. Partial splits preserve the source remainder, item properties and visibility, and total quantity. Invalid proposals fail as `invalid_response` and apply no inventory changes.
- Campaign resources now use strict panel transactions: quantity and money fields accept signed deltas applied against their locked canonical values; text, status, and date fields accept typed `set` operations. Every operation requires a reason. Negative results, zero deltas, duplicate fields, malformed operations, and untyped values fail atomically. Visibility-scoped history records field label, unit, before/change/after, and reason; the session timeline renders those details. The GM policy says ledger review alone is not a resource change.
- Campaigns persist campaign-scoped places with stable IDs, descriptions, JSON surroundings, and public or GM-private visibility. The starting world location seeds the player's first place, and a GM character's explicitly visible location seeds known presence.
- Public date, time, and weather aliases collapse to canonical fields at initialization, proposal validation, persistence, projection, and GM-context construction. A legacy conflict resolves from the latest matching public state-change audit event (and uses the existing header precedence when no such event exists); new proposals cannot supply two aliases for the same fact. New patches reconcile legacy state before applying the accepted change, so they cannot be overwritten by older aliases.
- The GM receives both visibility scopes for places and every character's current place. Place creation must precede movement; movement uses a known character and place, and the player cannot move to a GM-private place. Location changes commit with the turn. Generic world changes cannot overwrite the canonical location.

The location rail follows the player's canonical place even if a legacy world-location string is stale. Flexible item properties are shown as readable, escaped key/value details rather than raw JSON.
