## Goal and scope

Build a private, single-player TTRPG experience for new campaigns. Preserve the owner's Vineyard source unchanged and out of scope: never access, continue, import, or test against it or a comparison copy. Use only the campaign-independent play preferences already captured in project documentation, and use independently authored fictional QA campaigns for gameplay testing. The chosen MVP play surface is an independent Phoenix LiveView website running on the owner's computer, with game state stored locally. Model inference uses the owner's consented ChatGPT plan through OAuth while the app is running locally. Do not expose it as a remotely hosted service or share the OAuth credentials. One campaign can contain many play sessions; a session is a resumable segment of the campaign's continuous history. The first release supports one human player per campaign. Multiplayer, voice, maps, payments, and a general rule-system editor are outside the MVP.

The interface is a Phoenix LiveView application. It should update the turn timeline, character activity, world state, and campaign panels without full page reloads. Keep browser JavaScript small and limited to interactions that need it, such as optional die animation. Bind the web server and local database to loopback by default so the personal campaign site is not exposed to the network.

### Defining product promise: continuity is engineered, not entrusted to model memory

The owner's market research elevates this from an implementation detail to Storyteller's leading product thesis: an LLM should not be asked to remember or enforce the whole campaign by itself. Treat this as a hypothesis to validate through play tests and the product benchmark, rather than a proven claim about every competing product. The specific failure to design against is that a model may keep a character's personality vivid while losing a logistical fact as a long conversation is compressed: in the vineyard campaign, it remembers the employees well enough to give them jokes, but forgets that the Bodega is a forty-minute journey from the Finca. That makes charming narration contradict the established world.

Long-running campaigns should remain coherent because Storyteller stores and checks the world, not because a language model can recall every detail from a shrinking transcript. The application is the rules-and-canon engine; the model is the GM's expressive voice and proposes changes for the application to validate. Durable campaign state includes the facts the genre needs: character identity and presence, places and travel time, inventory and ownership, resources, commitments, and world time. The vineyard example is a product acceptance test: if the Bodega is a forty-minute trip from the Finca, staff who remain at the Finca do not appear at the Bodega to drop incidental dialogue. An accepted trip or another established means of contact must explain their presence.

Every turn gets a freshly assembled, bounded view of canonical state plus recent and relevant older story evidence. Canonical state is always retained in the local database; transcripts and summaries help retrieve context but do not override the ledger. The compiler prioritizes the current scene, connected places, present characters, relevant inventory/resources, applicable private GM facts, and action-related older events. It omits redundant or unrelated prose first, declares when older details were compacted, and never silently removes context. If the relevance pass still exceeds the byte preflight, progressively shorten older event narration while prioritizing the newest four events. Keep complete canon in local storage and validate proposals against it; only create a bounded request projection with explicit omission flags when relevance calls for it. If the bounded projection and prose compaction still cannot fit, fail the saved turn with a recoverable context-size explanation rather than asking the GM to guess. Diagnostics may contain sizes, section byte counts, and provider-reported aggregate usage only, never prompts, private facts, identifiers, or campaign text.

The inventory section is dedicated context and must not be duplicated inside public or GM-private world maps. Keep every item locally and validate all proposed inventory changes against the full ledger. In each GM request, preserve all item identities for lists of 16 or fewer; for larger lists include up to 10 action-relevant items plus six recent items. Include full descriptions/properties only for the strongest match per visibility, cap descriptions at 600 characters and property JSON at 700 bytes, and mark partial lists/details in `context_completeness`. The GM must not treat omitted items as absent or invent omitted properties. The player's inventory panel remains complete.

Spend context deliberately: avoid resending irrelevant biographies, unrelated history, or repeated state already represented in compact ledgers. Older conversation retrieval now anchors on the current and connected places, current-scene character speaker IDs, and a small set of action terms; it is local lexical/entity matching, not semantic search. The acceptance target is a bounded request whose actual provider input usage is observed where available and whose relevant canon survives long campaigns. The OAuth preview's separate input-token-count endpoint was rejected for this account, so byte-derived preflight bounds and completed-response aggregate usage are honest interim instrumentation; exact per-section token counts remain an open measurement improvement, not a claimed capability.

This is a product system, not a promise that an LLM can be made infallible: algorithmic guarantees apply to facts represented in Storyteller's canonical records and validations. For canon-critical or action-dependent gaps, the GM should preserve uncertainty or ask rather than turn a guess into canon. Ordinary present-tense sensory texture belongs to the GM and may be described when consistent with established facts; narrative omission alone does not establish absence. The transcript remains available as evidence, but a line of narration cannot by itself teleport a character, create or remove inventory, or overwrite a tracked resource. Player corrections to canon must have an explicit, reviewable path, including corrections to a campaign's current public date, time, or weather without rewriting the story or restarting play.

Canon should ground imagination without making every sparse scene feel like an empty record. When useful, the GM may add one or two ordinary, non-actionable sensory particulars—such as how light falls, a surface's color or texture, or ambient sound—consistent with the known place, time, and weather. On focused inspection, state observable details directly before interpretation; avoid turning an unmentioned detail into a claim that nothing is there. Ambient texture is not a clue or cause. It cannot introduce a person, owned or interactable item, exit or route, hazard, clue, service, or other actionable opportunity; those require accepted world state and, for a person, accepted presence. A clue may emerge from an established premise or current in-scene action; ground it in that event and propose it as public continuity when it matters. If a player's next action depends on canon-critical detail the campaign does not track, the GM should say so or ask rather than assume it exists.

For a focused inspection of an established object or place, the GM authors the present evidence that the character can observe from their action and vantage, even when that specific detail was not previously written into canon. Missing prior history or an unsupported cause can remain unknown; it is not a reason to ask the player to invent what they observe. Lasting action-grounded findings can be proposed as public continuity with event provenance. This distinction keeps the model from guessing hidden history while letting the GM run the world in the moment.

The campaign must also retain durable story facts that are not yet represented by a typed game ledger—for example, an established plan, promise, relationship, or explanation. Since an LLM can omit a fact from a proposed memory update, the player also needs a small, explicit way to preserve or correct these **public campaign memories** between turns. Both GM-authored continuity entries and player-managed notes persist with provenance; they are campaign state, not chat messages, and do not replace structured location, presence, inventory, or resource records. For each request, retrieve a bounded set of relevant details separately for public and GM-private entries; keep stable IDs, kinds, and statuses for other notes, mark omitted detail in context completeness, and treat missing detail as unknown. The full notes remain in their proper campaign panels, edits keep a reasoned audit trail, and private context never enters player-facing projections. This memory layer must close gaps without turning the player into the campaign's full-time archivist or resending the full note ledger on every turn.

Player agency includes who authors sensory facts. The GM describes what the character can observe—such as a wine's color, aromas, acidity, tannin, and finish—before inviting the character's reaction. Never ask the player to invent what the world or an object tastes, looks, sounds, or feels like. In particular, “What does it taste like?” makes the player supply a fact the GM should establish. Ask for the character's judgment or reaction only after describing the evidence. The player chooses their character's interpretation, words, and actions; that response does not by itself establish external world properties. Keep uncertain technical interpretations impressionistic; do not hedge what the character plainly perceives. Preserve a sensory finding as public continuity only when it matters to later play.

Scene pace must flex to intent and scope rather than using one fixed turn size. Stay close for direct questions, tense instants, and consequential choices, but let an in-character exchange reach its natural handoff rather than yielding after the first NPC action or line. Keep narration cohesive and dialogue proportionate to the beat: routine solo actions should not become round-robin chatter, while a player-invited ensemble may include each relevant present character's distinct reaction in the same beat. This is scene guidance, not a fixed speech-bubble count. Do not end every ordinary turn with a formulaic question. Let ongoing work or an explicitly uninterrupted interval resolve as one coherent scene at its requested scale, with meaningful progress and relevant present-character reactions together. A dialogue-only response may omit narrator prose when a character's reply completes the beat; group adjacent lines from the same speaker into one bubble, preserving alternating speakers. Establish sensory facts before asking for the player's subjective reaction. Skip repeated micro-actions and stop at the next genuine player decision. If scope is unclear, resolve only the immediate consequence; never supply the player's follow-through. Review independently authored fictional scenes for routine multi-day work, a focused inspection, and an ensemble social or live-event exchange, and measure prompts-to-decision as well as player agency, scene progress, continuity, and latency. Treat the scene-shape guidance as an unverified hypothesis, not a quality win; matched human play review must check that it reduces routine chatter without flattening dialogue-led/ensemble play. A connected Quiet Observatory spot check on 2026-10-04 produced one cohesive chart-analysis beat with two distinct NPC reactions, preserved uncertainty and prior evidence, and left the next lead implicit rather than forcing a formulaic question. That single service-level turn took 35.6 seconds; it does not verify first-token timing, LiveView streaming, or overall story quality. The earlier connected retry exposed a missing objective response contract; the bounded retry completed after that contract was added. Continue matched story and latency review across all three scene types. Preserve the source campaign text outside the repository.

Token economy is part of the same feature, not a later optimization. Keep durable detail in the local campaign database and send only the compact rules plus scene-relevant canon and history needed for the current action. Treat the configured byte ceiling as a conservative preflight limit rather than a token count; observe aggregate usage from successful provider responses when supported, and use representative long-campaign tests to prevent ordinary actions and questions from failing as the transcript grows. If the first compact view exceeds the byte ceiling, retain canon and progressively compress older narration, long-form reference prose, and stale ledger detail before asking the player to edit anything. A final emergency pass also shortens overlong remaining detail in the bounded request view, with explicit completeness metadata, while preserving the submitted player action and scene anchors; the original campaign data is never modified. Current usage is emitted through transient local telemetry and is not a durable per-turn report; any later usage history must store numeric counts only. Preserve identities, visibility, and state before trimming descriptive detail. If an irreducible scene still cannot fit, preserve the saved action and offer a specific review-and-retry path instead of silently dropping facts or asking the model to invent them.

**P0 request-size safeguard:** A local byte-preflight failure is not evidence that GPT or the player's ChatGPT plan rejected a request; it means Storyteller did not send it. The interim default is now **64,000 serialized bytes**, application-defined and uniform across configured model IDs. It admits the known 31,825-byte valid synthetic setup shape, but is not a model context window, account limit, or verified SIWC route maximum; route-specific calibration remains open. Treat this guard as something to validate, never as the normal capacity of a campaign or a reason to make players prune their notes. Ordinary actions and questions in a growing campaign must remain playable through relevance-first projection and safe compaction. Keep the complete ledger in the database; send a compact present-scene snapshot and retrieve older or off-scene facts only when the action makes them relevant. Do not rely on prior ChatGPT-thread memory to fill gaps: the current HTTP plan-usage flow requires each request to include its needed context and does not support `previous_response_id`.

The current request projection now has explicit growth limits: at most 48 character identities with up to 12 detailed profiles, 64 place identities with up to five detailed places, 48 objective identities per visibility with up to eight detail records, and a bounded recent/relevant slice of continuity identities. “Nearby” means the player's current location and routes directly connected to it; a place several route steps away is not treated as present-scene context just because it appears in the travel graph. Each limit prioritizes the player action and present scene, and completeness flags mark partial rosters or details. These are bounded request views only; the complete, visibility-scoped records remain durable and authoritative. When canon detail is omitted, the GM can use one request-scoped, read-only function that searches only the already-authorized campaign context and returns a small, visibility-labelled result. The app never accepts a campaign ID or broader visibility scope from the model.

The ChatGPT-plan HTTP route requires each request to carry its needed context and does not support previous_response_id; hosted MCP/connectors and tool_search are unsupported. Storyteller therefore uses an app-defined, local read-only function—not a hosted MCP—to retrieve a narrowly relevant fact from the current campaign's already-loaded canon. It is offered when the prompt omits relevant canon, including through an emergency compact scene packet if the full projection or its lookup reserve cannot fit. The packet marks omitted canon unknown, preserves the player's action and current public scene anchors, and directs the GM to retrieve before relying on omitted facts. When the present cast is larger than the packet's fixed roster cap, prioritize NPCs explicitly addressed by name, then those matched by public character details or visible activity, then recent speakers, before stable-order scene cast. Match whole name tokens so an unrelated word that merely appears inside a longer NPC name does not displace the actual addressee. Retain the truncation flag and lookup path for everyone omitted. The executor is bound server-side to the active campaign; the model cannot select campaign IDs, mutate state, or widen visibility. Continuation replays the original input and full prior response output, including reasoning, with a matching tool result ID and no provider-side persistence. For HTTP streams whose terminal `response.completed` event omits its output array, reconstruct the completed output from preceding `response.output_item.done` events so text and local function calls survive through validation and continuation. The adapter caps lookup arguments/results and checks the exact serialized request body before both the opening and continuation calls. Search terms are applied before long fields are excerpted, so a matching canon fact deep inside a long note can be returned in a bounded query-centered excerpt instead of being lost to prefix-only truncation. The tool schema/result and extra round trip still consume input and time; neither lower total tokens nor lower latency is assumed. Compare matched synthetic-campaign turns with the deterministic relevance-first baseline, including total serialized bytes, provider-reported aggregate tokens, round trips, latency, fact recall, privacy, and provenance. If even the compact packet and reserved lookup cannot fit, preserve canon and the saved action and offer a category-specific app-assisted review path rather than asking the player to hand-edit campaign notes.

For every MVP iteration that touches memory or state, apply the same continuity loop: represent durable facts once as structured, stable records; validate proposed changes against those records and explicit world constraints; commit accepted changes atomically with provenance; then assemble a bounded prompt from the current scene and only relevant older evidence. Keep the complete campaign locally, but do not resend it. Test both sides of the promise together: a relevant old fact must survive a long, cross-session campaign, while unrelated history must not grow an ordinary request past its configured bound. If required canon will not fit, preserve it and fail with a recoverable explanation. Use behavioral scenarios such as the Finca/Bodega journey to decide whether the game is coherent; use serialized byte ceilings and provider-reported aggregate usage to monitor cost. Never describe byte counts as exact token counts or claim the model can be made hallucination-proof.

**Continuity guarantee:** canonical presence and route-time validation prevent a character from casually appearing in a scene from another place. Public NPC dialogue and activity require a known player scene and canonical co-presence; a missing or unknown player place is not evidence that any NPC is there. Owners may place a GM character on one explicit duty at their current canonical place. An indefinite duty blocks departure until a reasoned, revision-checked owner correction; a finite duty stores an absolute release threshold anchored to the durable elapsed-world-minute clock. Movement checks the clock before the current turn advances it, so a departure cannot expire its own duty. Once an earlier accepted turn has advanced the clock to the threshold, later movement is allowed and still uses the canonical route duration. Duty details and completion status are supplied only to GM context, never player projections or story events. Free-form schedules remain narrative guidance rather than enforceable rules; campaigns without an assignment remain flexible.

**Narration presence safeguard:** reject clear narration-only physical-presence claims about public off-scene characters even when the GM uses one unique distinctive token from a multiword character name. A shared/ambiguous token or common role/title word alone cannot identify a character. This is a small lexical English, Spanish, and French safeguard, not general language understanding; ambiguous narration remains a human-review risk.

Remote communication is a separate, explicit path in public campaign canon. A known NPC can establish a sender-to-player path only while present with the player and speaking a public line that exactly matches the operation's cited basis text and plainly names the usable endpoint; the channel and endpoint are then saved in the backup-serialized public state. `public_changes` and separator/case-normalized aliases cannot seed or edit the path ledger. Establishment and deactivation each add a public before/after `state_change` audit event in the same transaction, outside the story timeline. GM context includes at most 12 active paths, ranking query-matched paths first and recent paths next. A remote delivery must reference an already active path for that sender and is recorded as its own `remote_message` event. It cannot create its own path, move any character, change the world clock, or alter routes. Ordinary off-scene NPC dialogue and activity continue to require canonical scene presence.

**MVP quality gate:** after an employee remains at the Finca while the player travels to the Bodega, the employee cannot join the scene or speak there until a valid route or established communication explains it. Remote communication must use a previously accepted public sender-to-player path: establish it with an in-scene, public NPC utterance and matching cited text, then require that active path's ID on every remote delivery. A remote delivery leaves locations, routes, and elapsed time unchanged and appears as a distinct message event, never NPC dialogue. Missing, inactive, or sender-mismatched paths fail before commit. A finite duty is anchored to the stored elapsed minute at assignment/edit; a route-valid departure is rejected while that threshold is still ahead, even if the same proposal includes enough time to cross it. A separate accepted turn may advance the clock to/past the threshold, after which a subsequent departure succeeds with the canonical 40-minute route time. A 0-minute edit completes the existing assignment immediately; clearing the duty releases it. Duty state remains private, reasoned, revision-checked, durable, and portable: backup v11 stores finite-duty thresholds plus communication-path state and remote-message events; v1–v10 imports remain supported. Across a later session, an older relevant public memory (such as the agreed work plan) remains available to the GM even if a prior model response omitted it from its continuity proposal. An unrelated old fact does not get resent on every turn. A reasoned correction to a visible date, time, or weather label updates the player board and future GM context without adding a story event or changing elapsed minutes; relabeling the date/time re-anchors the clock without reinterpreting elapsed time. These tests measure both coherence and context economy; token use is instrumented from supported provider usage, while the serialized-byte limit is treated only as a conservative preflight proxy.

### Model effort and latency guardrail

New and existing installations now default to GPT-6 Luna (`gpt-6-luna`); Automatic remains available as an explicit choice and selects the first displayable model returned by the connected account catalog. Storyteller requests `reasoning.effort: low` for GPT-5, GPT-6, and o-series identifiers; other selected models keep their defaults. Every GM request asks Responses for a JSON object, which prevents malformed JSON syntax but does not guarantee the application schema or canon is valid; Storyteller's complete validation remains mandatory. The compiler conservatively budgets reasoning and formatting fields in the exact request envelope before automatic catalog resolution, and the adapter adds them to the actual request. The current SIWC preview lists unsupported fields but not `text.format`; live route confirmation remains open. Earlier connected isolated QA measured GPT-6.1-Sol low at 32.8 seconds for an opening and 34.2 seconds for an action; manually selected GPT-6-Luna low took 7.2 seconds for a question, 8.9 seconds for an action, and 9.1 seconds for a one-hour passage. Those turns were not matched and do not prove equivalent story quality. API token prices do not define usage against a ChatGPT plan. Routine development and automated tests must use fake providers with no live model calls; if the owner explicitly requests a live exploration, use Luna at low effort. Sol/Astra comparisons require an explicit request for those models. The [SIWC inference guide](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference) documents catalog order and supported request fields; recheck current [preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations) before relying on new fields.

Reduce the *perceived* wait without implying that inference itself is faster. While a response streams, the play screen may show only the bounded, top-level GM narration field as a clearly marked provisional draft (“may change”). Never expose raw structured output, dialogue proposals, state changes, tool arguments/results, or private context in this preview. It is transient presentation only: do not persist it, append it to campaign history, apply it as canon, or include it in recovery context. Clear the preview when a new attempt begins or a stream fails; once validation and commit finish, replace it with the ordinary persisted timeline entry. If the response has no safely parseable narration yet, keep the existing in-progress status instead of guessing at the partial response. ### Retry and saved-action guardrail

Do not adopt a retry policy that makes a player's saved move fail and asks them to operate the recovery UI after an ordinary transient outage. The one quick retry is per claim, not a total retry cap: the session LiveView keeps safely transient network, incomplete-stream, provider-unavailable, and receive-timeout failures on the same saved turn through automatic cooldown recovery, with a growing delay capped at five minutes rather than a fixed claim ceiling. After the first four claims, recovery uses one half-open provider probe per cooldown. Recheck plan usage and active-turn ownership before every claim; preserve the exact action and roll, and commit canon only once after validation. The board keeps the action visible and says recovery is automatic; opening or reconnecting the session resumes an eligible failed turn, and a resolver crash gets its own recoverable diagnosis. Stop automatic calls for account/authentication or usage pauses, context-size interventions, malformed proposals, and other non-transient failures. A definitive rejected request should not be replayed unchanged; fix the request shape or provide a useful same-turn remedy rather than making the player re-enter their action. These cases must keep the original action available. Current limitation: the Quiet Observatory opening still received HTTP 400 with `param=input` after switching to the Responses guide's ordinary string-content message form. The current SIWC documentation confirms this app's public `POST /v1/responses` endpoint, `store: false`, `stream: true`, array input, and simple user text-item shape; the failing probe had one such item and no lookup tool. The error response had no code, diagnostic message, or request ID. Because the documented unsupported-capability recovery requires the machine-readable code as well as the parameter, `param=input` alone does not identify a safe payload change. `reasoning.effort` and `text.format` are not listed as unsupported, but the SIWC guide does not explicitly demonstrate them. Keep this an unresolved route compatibility issue, not a transient failure. The adapter records safe error categories and body-size/item-shape metrics without raw error or campaign text. Do not spend more live allowance on identical probes; make a concrete, evidence-based payload correction before one Luna-low confirmation attempt. This avoids a player click for a transient outage without creating a rapid unbounded request loop; continue QA on recovery rate, provider usage, total wait, and stop conditions. Any retry must preserve the submitted action, roll, and canon without duplicating committed events.

## Technical design for the selected local site

Use Phoenix, LiveView, Ecto, and PostgreSQL. A small set of domain contexts should own campaigns/sessions, characters/world state, turn resolution, rolls, and AI integration. LiveViews render and dispatch actions; domain functions enforce rules and persistence.

Suggested records: owner account, campaign, session, character, turn, roll, world-state snapshot, campaign field definition/value, and GM run metadata. Core relationships and frequently queried fields belong in typed columns. Flexible campaign-specific state can use validated JSON fields. Split public and GM-private facts at the data boundary and check visibility before rendering.

For each player action:

1. Persist one pending turn with an idempotency key and lock that campaign's resolution path.
2. Build model context from the versioned GM policy, editable campaign setup and per-character voice instructions, canonical state, relevant recent turns, and a maintained summary of older history. Store enough local history to resume without depending on provider conversation retention.
3. Request a structured GM response: narration blocks, attributed dialogue, character activities, proposed state changes, and either a roll request or a final outcome. Treat model output as a proposal; validate speaker IDs, visibility, units, allowed changes, and schema before applying it.
4. If a player roll is requested, pause the turn. Accept the player's die click, record the server-generated result, and continue resolution with that result. GM-controlled rolls use the same audited roll service without a player click.
5. Commit the accepted output, roll references, and state changes together. Publish the completed turn to LiveView. On timeout or invalid output, keep the previous canonical state, surface a recoverable error, and retain diagnostics without storing secrets.

For the selected local route, use the OpenAI Responses API behind the provider behaviour with a bearer token issued by the ChatGPT-plan OAuth flow. Stream each GM response and validate it before applying state changes. Verify the exact supported output format and tool-call shape in the feasibility milestone; if structured output fields are unsupported, use a supported function/custom tool or parse a constrained text payload and validate it locally. The database remains authoritative for campaign continuity. Keep the conventional API-key provider as a possible future adapter, but do not make its credentials or billing the MVP default.

## Risks and decisions to track

- **Account access:** The chosen OAuth route is a preview for eligible open-source, locally hosted apps. The user's Plus allowance is shared with other apps and can stop GM requests at a usage limit; the app must pause cleanly and must not switch to billed API calls. Remote hosting requires a separate eligibility process. Conventional API-key usage is a future option only if the owner changes the budget.
- **Protected source:** Preserve the owner's Vineyard source outside Storyteller. Do not access, request, export, summarize, continue, import, or test against it or a comparison copy. Gameplay QA uses independently authored fictional campaigns; only campaign-independent preferences already recorded in project documentation guide the experience.
- **Model fallibility:** A structured or constrained response reduces parsing ambiguity but does not guarantee correct fiction or arithmetic. Validate changes, keep the canonical state in the application, and preserve a reviewable event record.
- **Continuity drift:** LLM-generated summaries can omit, merge, or contradict details. Stable item, location, character, and relationship records plus event-linked state deltas are required before relying on the product for a long-running campaign.
- **Session meaning:** This plan treats a session as a segment inside a campaign. Confirm that model during the creation-flow review if the owner intends independent branches instead.
