# Storyteller MVP implementation plan

> **Selected direction (2026-09-29):** Build a standalone Phoenix LiveView site that runs locally and use Sign in with ChatGPT's preview ChatGPT-plan usage flow for GM inference. The owner has ChatGPT Plus and does not plan to buy API credits. This route is for eligible open-source, locally hosted apps, and has preview limitations and shared plan usage limits. Confirm eligibility and the GM request shape in the first implementation milestone before building the full turn loop. A conventional API-key integration remains a separately priced fallback only if the owner's budget changes.

## Goal and scope

Build a private, single-player TTRPG experience that can continue the existing vineyard campaign and host new campaigns. The chosen MVP play surface is an independent Phoenix LiveView website running on the owner's computer, with game state stored locally. Model inference uses the owner's consented ChatGPT plan through OAuth while the app is running locally. Do not expose it as a remotely hosted service or share the OAuth credentials. One campaign can contain many play sessions; a session is a resumable segment of the campaign's continuous history. The first release supports one human player per campaign. Multiplayer, voice, maps, payments, and a general rule-system editor are outside the MVP.

The interface is a Phoenix LiveView application. It should update the turn timeline, character activity, world state, and campaign panels without full page reloads. Keep browser JavaScript small and limited to interactions that need it, such as optional die animation. Bind the web server and local database to loopback by default so the personal campaign site is not exposed to the network.

### Defining product promise: continuity is engineered, not entrusted to model memory

The owner's market research elevates this from an implementation detail to Storyteller's leading product thesis: an LLM should not be asked to remember or enforce the whole campaign by itself. Treat this as a hypothesis to validate through play tests and the product benchmark, rather than a proven claim about every competing product. The specific failure to design against is that a model may keep a character's personality vivid while losing a logistical fact as a long conversation is compressed: in the vineyard campaign, it remembers the employees well enough to give them jokes, but forgets that the Bodega is a forty-minute journey from the Finca. That makes charming narration contradict the established world.

Long-running campaigns should remain coherent because Storyteller stores and checks the world, not because a language model can recall every detail from a shrinking transcript. The application is the rules-and-canon engine; the model is the GM's expressive voice and proposes changes for the application to validate. Durable campaign state includes the facts the genre needs: character identity and presence, places and travel time, inventory and ownership, resources, commitments, and world time. The vineyard example is a product acceptance test: if the Bodega is a forty-minute trip from the Finca, staff who remain at the Finca do not appear at the Bodega to drop incidental dialogue. An accepted trip or another established means of contact must explain their presence.

Every turn gets a freshly assembled, bounded view of canonical state plus recent and relevant older story evidence. Canonical state is always retained in the local database; transcripts and summaries help retrieve context but do not override the ledger. The compiler prioritizes the current scene, connected places, present characters, relevant inventory/resources, applicable private GM facts, and action-related older events. It omits redundant or unrelated prose first, declares when older details were compacted, and never silently removes required canon. If the required state cannot fit the configured safe input bound, the saved turn fails with a recoverable context-size explanation; it must not ask the model to guess. Diagnostics may contain sizes, section byte counts, and provider-reported aggregate usage only, never prompts, private facts, identifiers, or campaign text.

Spend context deliberately: avoid resending irrelevant biographies, unrelated history, or repeated state already represented in compact ledgers. Older conversation retrieval now anchors on the current and connected places, current-scene character speaker IDs, and a small set of action terms; it is local lexical/entity matching, not semantic search. The acceptance target is a bounded request whose actual provider input usage is observed where available and whose relevant canon survives long campaigns. The OAuth preview's separate input-token-count endpoint was rejected for this account, so byte-derived preflight bounds and completed-response aggregate usage are honest interim instrumentation; exact per-section token counts remain an open measurement improvement, not a claimed capability.

This is a product system, not a promise that an LLM can be made infallible: algorithmic guarantees apply to facts represented in Storyteller's canonical records and validations. For an unmodeled detail, the GM should preserve uncertainty or ask rather than turn a guess into canon. The transcript remains available as evidence, but a line of narration cannot by itself teleport a character, create or remove inventory, or overwrite a tracked resource. Player corrections to canon must have an explicit, reviewable path, including corrections to a campaign's current public date, time, or weather without rewriting the story or restarting play.

Canon should ground imagination without making every sparse scene feel like an empty record. When useful, the GM may add one brief, non-actionable sensory impression—such as light, ambient sound, smell, or general atmosphere—consistent with the known place, time, and weather. This is scene texture, not a new canonical fact. It cannot introduce a person, owned or interactable item, exit or route, hazard, clue, service, or other actionable opportunity; those require accepted world state and, for a person, accepted presence. If a player's next action depends on a detail the campaign does not track, the GM should say so or ask rather than assume it exists.

The campaign must also retain durable story facts that are not yet represented by a typed game ledger—for example, an established plan, promise, relationship, or explanation. Since an LLM can omit a fact from a proposed memory update, the player also needs a small, explicit way to preserve or correct these **public campaign memories** between turns. Both GM-authored continuity entries and player-managed notes persist with provenance; they are campaign state, not chat messages, and do not replace structured location, presence, inventory, or resource records. For each request, retrieve a bounded set of relevant details separately for public and GM-private entries; keep stable IDs, kinds, and statuses for other notes, mark omitted detail in context completeness, and treat missing detail as unknown. The full notes remain in their proper campaign panels, edits keep a reasoned audit trail, and private context never enters player-facing projections. This memory layer must close gaps without turning the player into the campaign's full-time archivist or resending the full note ledger on every turn.

Token economy is part of the same feature, not a later optimization. Keep durable detail in the local campaign database and send only the compact rules plus scene-relevant canon and history needed for the current action. Treat the configured byte ceiling as a conservative preflight limit rather than a token count; observe aggregate usage from successful provider responses when supported, and use representative long-campaign tests to prevent ordinary actions and questions from failing as the transcript grows. Current usage is emitted through transient local telemetry and is not a durable per-turn report; any later usage history must store numeric counts only. Preserve required canon before trimming low-relevance prose. When canonical facts alone exceed the safe bound, fail softly and explain the limitation instead of silently dropping facts or asking the model to invent them.

For every MVP iteration that touches memory or state, apply the same continuity loop: represent durable facts once as structured, stable records; validate proposed changes against those records and explicit world constraints; commit accepted changes atomically with provenance; then assemble a bounded prompt from the current scene and only relevant older evidence. Keep the complete campaign locally, but do not resend it. Test both sides of the promise together: a relevant old fact must survive a long, cross-session campaign, while unrelated history must not grow an ordinary request past its configured bound. If required canon will not fit, preserve it and fail with a recoverable explanation. Use behavioral scenarios such as the Finca/Bodega journey to decide whether the game is coherent; use serialized byte ceilings and provider-reported aggregate usage to monitor cost. Never describe byte counts as exact token counts or claim the model can be made hallucination-proof.

**Continuity guarantee:** canonical presence and route-time validation prevent a character from casually appearing in a scene from another place. Public NPC dialogue and activity require a known player scene and canonical co-presence; a missing or unknown player place is not evidence that any NPC is there. Owners may place a GM character on one explicit duty at their current canonical place. An indefinite duty blocks departure until a reasoned, revision-checked owner correction; a finite duty stores an absolute release threshold anchored to the durable elapsed-world-minute clock. Movement checks the clock before the current turn advances it, so a departure cannot expire its own duty. Once an earlier accepted turn has advanced the clock to the threshold, later movement is allowed and still uses the canonical route duration. Duty details and completion status are supplied only to GM context, never player projections or story events. Free-form schedules remain narrative guidance rather than enforceable rules; campaigns without an assignment remain flexible.

**Narration presence safeguard:** reject clear narration-only physical-presence claims about public off-scene characters even when the GM uses one unique distinctive token from a multiword character name. A shared/ambiguous token or common role/title word alone cannot identify a character. This is a small lexical English, Spanish, and French safeguard, not general language understanding; ambiguous narration remains a human-review risk.

Remote communication is a separate, explicit path in public campaign canon. A known NPC can establish a sender-to-player path only while present with the player and speaking a public line that exactly matches the operation's cited basis text and plainly names the usable endpoint; the channel and endpoint are then saved in the backup-serialized public state. `public_changes` and separator/case-normalized aliases cannot seed or edit the path ledger. Establishment and deactivation each add a public before/after `state_change` audit event in the same transaction, outside the story timeline. GM context includes at most 12 active paths, ranking query-matched paths first and recent paths next. A remote delivery must reference an already active path for that sender and is recorded as its own `remote_message` event. It cannot create its own path, move any character, change the world clock, or alter routes. Ordinary off-scene NPC dialogue and activity continue to require canonical scene presence.

**MVP quality gate:** after an employee remains at the Finca while the player travels to the Bodega, the employee cannot join the scene or speak there until a valid route or established communication explains it. Remote communication must use a previously accepted public sender-to-player path: establish it with an in-scene, public NPC utterance and matching cited text, then require that active path's ID on every remote delivery. A remote delivery leaves locations, routes, and elapsed time unchanged and appears as a distinct message event, never NPC dialogue. Missing, inactive, or sender-mismatched paths fail before commit. A finite duty is anchored to the stored elapsed minute at assignment/edit; a route-valid departure is rejected while that threshold is still ahead, even if the same proposal includes enough time to cross it. A separate accepted turn may advance the clock to/past the threshold, after which a subsequent departure succeeds with the canonical 40-minute route time. A 0-minute edit completes the existing assignment immediately; clearing the duty releases it. Duty state remains private, reasoned, revision-checked, durable, and portable: backup v11 stores finite-duty thresholds plus communication-path state and remote-message events; v1–v10 imports remain supported. Across a later session, an older relevant public memory (such as the agreed work plan) remains available to the GM even if a prior model response omitted it from its continuity proposal. An unrelated old fact does not get resent on every turn. A reasoned correction to a visible date, time, or weather label updates the player board and future GM context without adding a story event or changing elapsed minutes; relabeling the date/time re-anchors the clock without reinterpreting elapsed time. These tests measure both coherence and context economy; token use is instrumented from supported provider usage, while the serialized-byte limit is treated only as a conservative preflight proxy.

**MVP workstream — prove continuity at a deliberate context cost:** treat this as one product goal with two simultaneous acceptance dimensions, not a memory feature followed by a later cost pass. For each new state category, decide whether it needs an authoritative typed record, a compact retrievable story memory, or narrative-only treatment; validate model-proposed changes against authoritative records before committing them. Assemble each turn from required current canon and the smallest relevant slice of older evidence, keep the full record locally, and trim irrelevant prose before required facts. Continue closing the documented gaps in routine character availability and cross-language/implicit-reference retrieval. Broaden deterministic query aliases only with bounded, reviewed vocabulary and behavioral coverage that proves both paraphrased relevant-memory recall and omission of unrelated notes; broad semantic paraphrase still needs evaluation. The current bounded social slice adds English, Spanish, and French meeting/reply cues for typed future-meeting and future-reply commitments, including French present-plural forms like “se rencontrent” and “se retrouvent”; behavioral decoys keep ordinary facts and unrelated notes out. A generic work-plan query now has a bounded exception: reviewed English, Spanish, and French plan/intention cues retrieve active typed commitments without requiring the original subject nouns; completed commitments and ordinary facts remain compact metadata, and the existing eight-detail-per-visibility cap still applies. The seasonal vocabulary covers later-session reserve questions in Spanish (“¿Qué guardamos para la cata de otoño?” and “¿Qué apartamos para la cata de otoño?”), English (“What did we save for the autumn tasting?”), and French (“Qu’avons-nous gardé pour la dégustation d’automne ?”). Each retrieves an older public reserve fact while same-tasting schedule/menu details retain metadata only, within the 24,000-byte preflight bound. More indirect phrasings and general semantic retrieval remain outside coverage. On short and long synthetic campaigns, verify that an older relevant fact survives while unrelated events do not inflate ordinary requests; compare the bounded request with the full-history baseline, collect actual aggregate provider usage when available, and use serialized bytes only as a clearly labeled conservative proxy. A fake-provider regression now exercises the production `Play.submit_turn` boundary across 100 sessions and 2,400 persisted events, retaining an older Finca/Bodega travel-and-duty fact plus all 12 newest events while keeping the compact request within budget and below one-fifth of the full-history serialized-byte baseline. If required canon cannot fit safely, keep it intact and offer a recoverable failure instead of silently dropping it or asking the GM to guess. The Finca/Bodega scenario is the representative player-value test: a character's personality never substitutes for canonical location, travel, or duty. Measure prompt size and false retrieval alongside continuity, and never reduce context cost by removing facts needed to play coherently.

**Additional demonstrated query cues:** production-boundary fake-provider coverage verifies that later-session “What did we decide?” questions recall an old agreement, and “What was our plan again?” recalls an active old plan even without shared subject nouns. Reviewed English, Spanish, and French decision and plan/intention forms are covered. Same-topic ordinary facts and completed commitments do not expand from generic plan wording; details remain capped at eight entries per visibility, and each tested request stays within the configured input-token budget according to the conservative serialized-byte upper bound. Other paraphrases and broad semantic retrieval remain open; these cues are not a general intent detector.

The same bounded retrieval now recognizes reviewed English, Spanish, and French “what should we do next?” phrasing and recalls active typed commitments across sessions. Same-topic ordinary facts and resolved commitments retain metadata only. Production-boundary regression covers the commitment’s source-event provenance and decoy omission while staying within the same conservative request bound; more indirect paraphrases remain open.

## Release roadmap

- **MVP — owner-run local game:** Finish and polish the single-player campaign experience around the existing GPT/ChatGPT plan-usage route. The release-critical continuity workstream is to make the application own and validate modeled world state while the GM model narrates and proposes changes; feed it the smallest relevant, bounded context that supports coherent play. Explicit finite and indefinite GM-character duties now gate movement against canonical elapsed world time, while reasoned owner corrections remain available. Remaining work includes deciding which other routine availability constraints deserve typed records, improving cross-language and indirect recall without injecting unrelated memories, and validating context economy on long campaigns using behavioral regressions plus provider-reported aggregate usage where available. Keep campaigns in the durable local database; if required canon cannot fit safely, fail recoverably without omitting it. The app must not silently switch to paid API billing.
- **V1 — supported open-source release:** Once the game is polished, publish clear setup and operating instructions for local installations, including Windows/WSL, durable database setup and backup, OAuth configuration, upgrades, and recovery. Add Settings so each person running their own installation can connect their own GPT/ChatGPT account through the supported plan-usage flow and choose a preferred model from that account's available catalog. Until the operator chooses, preserve the current automatic model-selection behavior. Keep model controls out of the play board and the route's eligibility and account limits explicit; do not imply that a ChatGPT subscription includes paid API credits. Complete the deferred keyboard, screen-reader, and contrast review. The MIT license is already in place. Create the README and release documentation as part of this V1 work, not before.
- **V2 — additional AI providers:** Add other providers only after V1. Reuse a small, tested provider boundary and give each provider its own connection, model, and failure guidance; avoid provider-specific behavior leaking into campaign rules or persisted game canon. Choose providers and billing paths as a separate V2 decision.

### Bring-your-own AI account scope

V1 is an open-source release for people running Storyteller on their own machines. Each installation connects to the operator's own eligible GPT account from Settings; Storyteller must not ship with a shared project credential or ask users to place secrets in the repository. The initial V1 connection is the supported ChatGPT-plan OAuth flow described below. Be clear that eligibility and plan limits apply, and that a ChatGPT subscription does not include API credits. Do not imply that arbitrary GPT accounts or subscription tiers are supported until verified. V2 is where we decide and add connections for other AI providers; each person's provider account and any billing remain theirs to authorize.

### Portable campaign backups

Basic campaign export and restore are already implemented. Keep them as quiet, collapsed **Campaign persistence** sections: import at the bottom of the campaign library, so it remains available on a fresh installation, and export on each campaign's detail page. Do not treat additional backup work as an MVP milestone. The existing versioned file preserves game records, validates before import, creates a separate copy, and excludes OAuth credentials. Improve backup UX or operator recovery instructions only when play evidence shows a real recovery gap; whole-install backup guidance belongs in V1 documentation. Do not let maintenance features displace play testing or core-loop quality work.

### Open-source and secret-handling bar

- Never commit or publish OAuth access/refresh tokens, API keys, private keys, database credentials, real campaign exports, or account-specific diagnostics. Keep real values in protected local storage; redact them from logs, crash reports, screenshots, and support bundles.
- Ignore local environment/secret files in Git. Any future sample configuration must contain clearly fake placeholders only. Before V1 publication, review the full Git history and release artifacts for secrets and private campaign data, run an automated secret scan, and document credential storage, disconnect/rotation, backup, and data-removal steps.
- Keep examples, seeds, and automated tests fictional and credential-free. Public setup instructions must distinguish the GPT plan-usage route from separately billed API-key usage and explain that the app makes no unannounced billing fallback.

## Chosen play surface and account model

OpenAI lists Plus and conventional API-key use separately; API-key calls follow per-token pricing. The selected route is the documented [ChatGPT-plan usage flow for eligible open-source and locally hosted apps](https://developers.openai.com/siwc/token-sharing-open-source). It authorizes supported Responses API calls using an OAuth access token granted by the owner. It is in preview, shares the owner's Plus usage allowance with other ChatGPT apps, and does not grant access to existing ChatGPT conversations. Do not automate the ChatGPT website or reuse its browser session as a substitute. Keep the repository open source and verify the project's eligibility before relying on this route. If the site is later hosted remotely or offered as a paid app, OpenAI says to use its interest process; that is outside this plan.

The chosen product path is:

1. **Standalone local site with ChatGPT-plan OAuth:** Run Phoenix and its database on the owner's computer, open the site in the browser, and keep campaign content in the app's local database. The player interacts in the website, not in ChatGPT. The app signs in through OpenAI's open-source client flow and calls the public Responses API with the owner's OAuth bearer token. This is the preferred MVP and does not use an API key or per-token API billing, subject to eligibility, the preview's supported features, and Plus limits.

### OAuth and local credential requirements

- Keep the application open source and locally hosted. Before relying on the preview, confirm the current eligibility and any OSS registration terms. If the owner later wants remote access, remote hosting, or a paid distribution, treat that as a new product decision and obtain the required OpenAI eligibility first.
- First sign-in dynamically registers the local app using its actual app name and a persistent, opaque `ext_agent_host_id`; reuse the issued `client_id` for that ChatGPT account. Each distinct local host has its own stable host ID. This flow does not require an API key or client secret.
- Start authorization in the system browser using the documented loopback callback on `127.0.0.1`, OAuth authorization code with PKCE S256, fresh `state` and OIDC `nonce`, and the `https://api.openai.com/v1` resource. Request identity scopes plus `offline_access`, `resource.invoke`, and `chatgpt.tokens.use.direct`. Validate the callback, granted scopes, ID-token signature, issuer, audience, expiry, nonce, and account identity before enabling GM calls.
- Store the issued client ID, verified account identity, host ID, ID token, access token, refresh token, granted scopes, and expiries in protected local server-side storage. Never put credentials in browser storage, source control, logs, or analytics. Access tokens last one hour; refresh tokens last 30 days and rotate on successful refresh. Serialize refresh operations. Revoke the renewable session on sign-out and clear local tokens. A compromised account can disconnect the app from ChatGPT settings.
- Send inference requests only to `POST https://api.openai.com/v1/responses` with the OAuth bearer access token and a model available to the signed-in account. Load the account's available model list instead of hardcoding an unavailable model. Treat eligible responses as subscription usage, not API key spend.

### Preview request constraints

- For every HTTP Responses request, set `store: false` and `stream: true`, and send the complete needed context as an `input` array. Put GM instructions in `instructions` or developer messages; explicit system-role message items are rejected.
- Do not send `previous_response_id` or rely on provider-side conversation storage. The local database and summary builder are authoritative for campaign history and continuity.
- Omit unsupported request fields: `background`, `conversation`, `max_output_tokens`, `max_tool_calls`, `metadata`, `moderation`, `multi_agent`, `prompt`, `prompt_cache_retention`, `safety_identifier`, `temperature`, `top_logprobs`, `top_p`, `truncation`, and `user`.
- Use supported function/custom tools only, grouped in namespaces or supplied as `additional_tools` input items. The preview does not support hosted MCP/connectors, Responses `tool_search`, image generation, file search, Code Interpreter, native computer use, audio/video inputs, Files upload API, or transcription API. The MVP only needs text and app-side campaign state, so it should not depend on these hosted tools.
- Consume the stream through a terminal event and apply game changes only after `response.completed` and application validation. Handle unsupported-capability errors by correcting the request, not retrying the same body. On a usage-limit error, stop new GM requests and show the user where to check ChatGPT usage; do not silently fall back to paid API calls. On temporary usage-unavailable errors, preserve turn state and retry later with bounded backoff. If the account or workspace is ineligible, show the sign-in limitation and stop.

### Monthly inference cost estimate

The selected OAuth route has no separate per-token API charge; it consumes the owner's existing ChatGPT Plus allowance. The current listed Plus subscription is $20/month. The owner already has that plan, so Storyteller's estimated additional model charge on this route is $0/month while requests remain eligible and within plan limits. The Plus allowance is shared with other apps and work in the account, so price is predictable but available play capacity is not guaranteed. Local hosting avoids a hosting bill for the MVP if it runs on the owner's existing computer; domain, remote hosting, and any infrastructure the owner later chooses are excluded.

For comparison only, a conventional API-key route would add token charges to Plus. GPT-6 Luna standard rates are $0.10 per million uncached input tokens, $0.01 per million cached input tokens, and $0.50 per million output tokens for requests with up to 272K input tokens. The estimates below use uncached input, 30 play days per month, and the game's actual call pattern: one call for an ordinary player action, plus a second call only when the GM requests a player D20 and must resolve its result. The D20 roll and proposal validation are local and do not use the model.

Each request sends the fixed GM policy (about 3,000 tokens) plus campaign context: canonical world and character state, public and GM-private summaries, continuity records, and up to 40 recent event records. The history window is bounded rather than the whole transcript. Prompt sizes below are budgeting assumptions, not measured provider usage; real size varies with campaign content. The roll column assumes 15% of actions need a second call, an illustrative rate rather than a measured one:

| Short: 5/day | 12,000 / 1,500 | $0.29 | $0.34 | $20.34 |

The selected ChatGPT-plan OAuth route still adds $0 in API charges and uses the existing $20/month Plus plan allowance, shared with other ChatGPT apps. Its cash price is therefore the existing subscription, while the API figures above are only a metered-billing comparison. Prompt caching could lower API input costs when the request prefix qualifies; unusually large histories, repeated roll follow-ups, or retries could raise them. OAuth requests can instead pause at the account's plan limits, without purchasing API credits.

The input-size, roll-follow-up, cache, and post-MVP measurement assumptions are documented separately in [Inference cost investigation](docs/INFERENCE_COST_INVESTIGATION_2026-09.md). The GPT-6 Luna API rates are a low-cost comparison example, not a claim that its play quality matches another model or the ChatGPT-plan route.

## Preserve the vineyard game and its GM rules

1. Review the complete vineyard conversation or obtain an authoritative export. The original chat is accessible read-only through conversation history, but long retrieved messages may be truncated; do not reconstruct missing facts from partial messages.
2. Extract a dated timeline, player character, GM-controlled characters, relationships, locations, resources, commitments, open decisions, and current world state. Mark uncertain or conflicting facts for owner review. Import the approved result into a private campaign, with the source transcript retained as an archive outside the public Git repository.
3. Store the shared GM policy as the versioned, campaign-independent `docs/GM_POLICY.md`. The original vineyard conversation establishes these behaviours:
   - React to player actions with natural consequences; ordinary actions can remain ordinary.
   - Let scenes breathe. Escalation, mysteries, and revelations require an established cause or prior clues.
   - Give NPCs their own knowledge, motives, and agency.
   - Never decide the player's actions, speech, thoughts, or choices.
   - Roll only for uncertain, consequential actions. Ask the player to roll for player-controlled characters; resolve GM-controlled checks on the GM side.
   - Describe the outcome, let the world respond, and return control to the player.
   - The GM advances the calendar and weather, and every turn keeps the in-world date visible.
4. Separate that policy from each campaign's setting, tone, characters, and mechanics. During vineyard import, review any campaign-specific rules against the full transcript before treating them as canonical.

## Product behaviour

### Product quality priorities

#### MVP triage and delivery order

Use player value, confidence in the problem, and delivery effort to choose the next task. Atlassian's common prioritization guidance covers impact-versus-effort and RICE; because this is currently a one-player local product, do not invent reach scores or let a numerical RICE result outrank direct play evidence. Re-triage as each separate-campaign test reveals friction. This follows the game-production focus on protecting and polishing the core gameplay loop before ancillary scope, as discussed in GDC's production triage guidance ([GDC: The Art of “Triage” in Online Game Development](https://gdcvault.com/play/1027084/Principles-of-Game-Interface-Design); [Atlassian: product prioritization frameworks](https://www.atlassian.com/agile/product-management/prioritization-framework/)).

1. **Now — make a campaign feel good to play.** Prove the complete session loop in a separate fictional campaign: a GM-led opening; clear situation and relevant character/world board; intuitive act, ask, look, wait/pass-time and player D20 interactions; one coherent, paced GM response; readable direct character dialogue; and a clear next decision. Keep the player's submitted action visible while the GM responds. Preserve location, date/weather, characters, inventory/resources, rolls, and history across multiple sessions and app restarts. Canon integrity under a bounded GM context is a release gate within this loop: prioritize defects that lose an action, leave a turn stuck, contradict tracked facts, exceed the ordinary context bound, hide an important state change, steal player agency, or make the next move unclear.
2. **Next — strengthen weak parts of that loop.** Use observed play friction to refine GM prompting and character voice, scene pacing, message/history scrolling, relevant panel feedback, time passage, and recovery from plan limits or malformed AI responses. Fix campaign-setup or editing friction when it prevents starting or correcting a real campaign. Validate each change through a behavioral scenario rather than styling alone.
3. **Later — supporting polish and operations.** Keep backup import/export collapsed in their existing persistence sections; do not spend an MVP iteration adding backup options or presentation polish. Defer broad accessibility hardening and public release/operator documentation to V1, as planned. Maps, optional illustrations, analytics beyond what's needed for safe QA, and other AI providers remain later work unless play evidence elevates them; other providers are V2.

Use a short product gate after each play-test: can the player tell where they are and what matters, make their intended move without hunting, follow a paced GM answer, and trust the resulting state on return? Record the concrete player task, observed friction, and outcome. Appearance work supports these outcomes but does not outrank a broken or confusing turn.

- **Additional product goal — make play feel like a tabletop conversation.** Alongside the original goals of durable campaign play, player agency, flexible character state, continuity, recovery, and polished design, reserve the story for the player's actions, natural GM narration, direct character speech, and relevant roll prompts. Present a turn as a few connected story beats, not a burst of disconnected system-like messages. Keep canonical memory and state changes in their panels, introduce people through the scene, and narrate world changes while the authoritative indicators update.
- Deliver the full play experience, not just a beautiful shell: a player should be able to follow the campaign, understand their character's current situation, act with confidence, and pick up the same world later.
- Give the player a clear character board for their current place, surroundings, immediate situation, known character details, and owned items or resources. Present only information the character would know. Keep campaign-specific information configurable so the same interaction supports an adventurer's equipment and a vineyard's wine stock and cash.
- Treat the model as the narrator and proposer, not the source of truth. Durable world facts, character presence, possessions, resources, and accepted events live in the local database. Give the GM concise hidden context for private motives and unresolved facts, while deriving player views only from public state.
- Make algorithmic continuity a defining product advantage: Storyteller owns the world model, and the LLM performs within it. Track where people and things are, how places connect, how long travel takes, what has changed, and which characters can plausibly be present. Do not depend on the model retaining those facts from prose or prior turns.
- Validate state-changing proposals against canonical entities and safe campaign-defined schemas. Apply accepted changes atomically with a traceable event; reject unknown entities, invalid ownership or quantities, and unapproved changes. A narrative sentence must not silently create or remove a tracked item.
- Let players repair mistakes in campaign setup and public world canon after play begins. Date, time, weather, character locations, inventory, tracked resources, and public story notes need a reasoned audit path that updates future context but never rewrites past narration or silently advances game time.
- Benchmark both AI-native play tools and campaign-management tools before finalizing this information model. ### Campaigns and sessions

- Streamline campaign creation as a guided wizard: gather the story and player character in clear, compact steps, make optional world/character details easy to skip, preserve entered values when moving backward, and show a concise review before creation.
- Starting a newly created campaign must open with the GM setting the scene and introducing the immediate situation. The player should not have to invent the first prompt to make the world move; subsequent turns remain responsive to the player's actions and the GM's established pacing.
- The first usable campaign creation flow accepts a title, story premise, setting, tone, language, player character details, optional GM-controlled characters, initial location/date/weather, and any campaign-specific mechanics. A review step shows the setup before play begins.
- The owner can create, list, open, resume, and archive campaigns. Within a campaign they can start and switch between sessions without losing the continuous campaign state or turn history.
- Keep the existing backup and restore controls as low-priority maintenance: a collapsed **Campaign persistence** section on the library for import and a collapsed section on campaign details for export. Explain that backups contain private GM context and restores create a separate campaign; further backup feature work is not an MVP goal.
- Campaigns remain editable after play begins. Provide an easy-to-find editor for the story brief, language, player-character details, GM characters, voice guidance, and setup details; saved edits affect future GM context and never rewrite earlier turns.
- Give every GM-controlled character optional, character-specific GM voice guidance: quirks, accent or dialect, cadence, vocabulary, mannerisms, and conversational boundaries. Keep it distinct from public character facts, include it in future GM prompts, and keep the character recognizable without turning one trait into a caricature.
- Keep voice guidance inside each character's setup card in both campaign creation and the campaign editor. The GM should be able to set a name, facts, private notes, and optional delivery cues together while character-specific voice notes remain GM-only; avoid a separate campaign-wide voice section.
- Make the combined voice-note limit visible while editing. Show the per-character live character count and an inline warning when the five fields together exceed the server-enforced total, preserve the draft after rejection, and name both per-field and combined limits in the save error.
- Give the player character a distinct name and descriptive details. Campaign creation and editing should offer separate name/details fields; the character list should use only the name as its heading, while the description stays in the player's profile and GM context.
- Let the player correct campaign canon without starting over. Offer an explicit out-of-character correction path for tracked state and campaign setup, preserve the before/after and reason in an audit record, and show a concise correction receipt outside the fictional dialogue. Do not silently rewrite the past timeline.
- Give the GM a clear invitation to lead when the player is finished acting. Keep **Act or say** as the default, and offer a distinct **Ask the GM** mode for table questions such as “What do I see?” or “What happens if…?”; answering should clarify the current scene without silently advancing time or changing canon.
- Make common nudges available as contextual quick actions, with optional specifics when needed: look around, clarify a detail, wait, or let time pass. Time-passage actions must make their intent and duration clear, invite the GM to advance the world and relevant off-screen activity, and stop at a meaningful player decision instead of deciding what the player does.
- The play screen has a turn timeline, a text input for what the player does or says, a D20 control, a compact world-state header, a character activity area, and configurable campaign panels. The layout adapts to narrow screens.
- Submitting an action with Ctrl+Enter uses the same validated form path as the Send button; plain Enter continues to insert a newline.
- The player can switch between in-character actions and direct table questions, and can ask the GM to continue or let time pass using a small set of contextual nudges. Mode and nudge intent must be explicit in the saved request so the GM does not mistake a question for a character action or skip time without permission.

Interface preferences such as English/Spanish/French belong in a compact Settings menu, not beside the story as a primary action. Avoid repeated labels, setup/admin details, and state already clear from the board; keep a direct path to deeper reference when the player wants it.

A saved model may later become unavailable; surface the provider's model-unavailable response as a recoverable failed turn so the operator can change the setting or return to Automatic.
- Small scene cues help ground time and conditions in the imagined world (for example, a moon behind clouds with mist at midnight). Story entries arrive gently in the already-paced sequence, and a changed panel value gets a brief cue in place. Keep words authoritative and readable; imagery and motion support the game instead of demanding attention.

### Turns, characters, and the D20

- Each completed turn records the player's text, GM narration, NPC dialogue as speaker-attributed speech bubbles, the visible activity of relevant GM-controlled characters, world changes, and any rolls. The player-facing story stays conversational: structured state changes update their panels rather than appearing as system bubbles. The GM also maintains private facts and offstage activity without exposing spoilers in the player view.
- Persist each NPC's voice instructions with that character and include them by speaker ID in every relevant GM context. Test that characters with sharply different authored voices remain distinct across turns; a French beaver cook should sound like the character the player created, not like a generic narrator. Treat accent and quirks as optional guidance and avoid flattening the whole performance to a single gimmick.
- The player initiates each D20 roll by clicking the die. The server generates and records the result. When a player action needs a roll, the GM states what is being tested and the difficulty or target before the player rolls; the result then goes back into resolution. The GM never silently rolls for a player-controlled character. GM-controlled checks use a separate server-side roll path.
- A turn can be pending, awaiting a player roll, completed, or failed. Disable duplicate submissions, show progress while the GM responds, and allow a failed turn to be retried without duplicating events or applying state twice. A refresh or reconnect must restore the same pending or completed turn.

### World and campaign panels

- Maintain canonical, persisted state for location, in-world date/time, weather, characters, and campaign resources. Do not rely on prose or model memory as the only source of truth.
- Persist a separate elapsed-world-minute total. Accepted movement adds at least its server-computed route duration; sequential route legs sum per character and simultaneous character trips use the longest sum. A proposed `time_advance_minutes` is the whole turn's total including travel, and the committed amount is clamped to the canonical route floor. Ask GM must keep it zero; Time passage must provide a positive bounded amount. Keep the elapsed cue tied to the exact current free-form date/time label, without parsing fantasy calendar text or guessing day rollover. Failed turns never change the clock.
- Provide an at-a-glance, player-facing character board for the present scene and current character details. It should make place, surroundings, immediate activity, visible NPC presence, and character resources findable during play, without forcing players to scan the whole transcript.
- Support a flexible, campaign-defined inventory and resource model. Dungeon campaigns need named items, consumables, equipment, quantities, and ownership; a vineyard may need cash, wine stock, vine stock, or other domain-specific quantities. Track stable identities and ownership so updates change the correct item instead of an ambiguous label. Avoid arbitrary executable formulas in the MVP.
- Define safe field types, units, visibility, and editable schemas. Existing quantity, money, text, status, and date fields can cover simple ledgers, including cash and wine/vine levels, but they do not replace a first-class owned-item inventory when items have identity or per-character ownership.
- Keep a canonical place/character-presence record so an NPC's known location and a character's movement can be checked against accepted events. Show private GM facts only in prompts and never in player projections. Narrate meaningful date/weather changes in the scene; the world bar shows the canonical current values without a separate system message.
- Track optional campaign-scoped objectives with stable IDs, `open`, `completed`, and `abandoned` status, and public or GM-private visibility. The GM prompt receives both canonical visibility scopes; ordered, reasoned create/update proposals validate against prior operations and commit with their visibility-safe audit events. The player board shows public objectives by status across sessions.
- Keep an append-only record of player actions, rolls, GM outputs, and applied state changes, with current state snapshots for quick loading. Every visible value should be traceable to a turn or an explicit setup/edit action.

### GM continuity and canon

- Assemble each GM request from the versioned play policy, campaign setup, the latest canonical public state, the private GM state, typed character and inventory facts, current character locations, the most recent events across sessions, and separate public/private continuity summaries.
- Include the durable elapsed-world clock as compact GM context. This complements character presence and route ledgers: the Finca-to-Bodega route establishes a 40-minute minimum and also advances campaign elapsed time even when the campaign's free-form date/time phrasing is not machine-readable.
- Represent the world as structured, durable facts rather than a transcript the LLM must remember. At minimum, model campaign places and their known connections/travel durations, each character's canonical location and presence, and accepted arrivals, departures, and other meaningful movement. A bodega forty minutes from a finca stays forty minutes away; employees based at the finca cannot casually appear at the bodega unless an accepted world event puts them there. Where a campaign needs it, include explicit availability or routine constraints so off-screen characters act only from a plausible place and time.
- Build a bounded, scene-relevant context projection for each request. Include the current location and nearby/connected places, who is present, facts and resources relevant to the player's move, applicable private GM context, and a compact set of relevant recent or retrieved older events. Keep the complete canon and history in the database; retrieve older details by stable entity and event references instead of copying the whole transcript into every prompt.
- For an in-character action that explicitly travels to a named, public destination with a direct public route from the character's current public place and also asks to look around, retrieve older facts anchored to that destination in the same turn. Do not add that destination context for Ask GM, hypothetical travel, an unnamed destination, a private place/route, or a connected place the player is not traveling to. Keep unrelated off-scene clues omitted and stay inside the normal context bound.
- Treat summaries as navigation aids, not as replacements for canonical inventory, location, ownership, or unresolved facts. Older events remain inspectable even when they leave the bounded prompt window.
- Require proposed changes to identify stable records and explicit operations such as add, remove, transfer, move, or update. Validate quantities and permitted destinations before committing; record accepted deltas with the turn and refresh snapshot state atomically.
- Keep private facts in the GM context and private event history. Public timeline, character board, campaign panels, validation errors, and reconnect state must not disclose them.
- Enforce a deterministic per-model input safety bound, keep canonical records intact, and rank context by current scene and action relevance. Retrieve relevant older conversation evidence without loading the full transcript. Compact redundant prose and non-scene detail before any canonical data; if essential canon still cannot fit, fail the saved turn recoverably rather than inviting a guess. The current OAuth integration enforces a conservative UTF-8 byte-based upper bound and emits the provider's aggregate input/output token usage through transient local telemetry after successful responses; it does not persist per-turn usage or claim exact section-level tokenizer counts. Never log prompt text or private facts. Summaries aid navigation, while canonical records remain authoritative.

## Technical design for the selected local site

Use Phoenix, LiveView, Ecto, and PostgreSQL. A small set of domain contexts should own campaigns/sessions, characters/world state, turn resolution, rolls, and AI integration. LiveViews render and dispatch actions; domain functions enforce rules and persistence.

Suggested records: owner account, campaign, session, character, turn, roll, world-state snapshot, campaign field definition/value, and GM run metadata. Core relationships and frequently queried fields belong in typed columns. Flexible campaign-specific state can use validated JSON fields. Split public and GM-private facts at the data boundary and check visibility before rendering.

For each player action:

1. Persist one pending turn with an idempotency key and lock that campaign's resolution path.
2. Build model context from the versioned GM policy, editable campaign setup and per-character voice instructions, canonical state, relevant recent turns, and a maintained summary of older history. Store enough local history to resume without depending on provider conversation retention.
3. Request a structured GM response: narration blocks, attributed dialogue, character activities, proposed state changes, and either a roll request or a final outcome. Treat model output as a proposal; validate speaker IDs, visibility, units, allowed changes, and schema before applying it.
4. If a player roll is requested, pause the turn. Accept the player's die click, record the server-generated result, and continue resolution with that result. GM-controlled rolls use the same audited roll service without a player click.
5. Commit the accepted output, roll references, and state changes together. Publish the completed turn to LiveView. On timeout or invalid output, keep the previous canonical state, surface a recoverable error, and retain diagnostics without storing secrets.

For the selected local route, use the OpenAI Responses API behind the provider behaviour with a bearer token issued by the ChatGPT-plan OAuth flow. Stream each GM response and validate it before applying state changes. Verify the exact supported output format and tool-call shape in the feasibility milestone; if structured output fields are unsupported, use a supported function/custom tool or parse a constrained text payload and validate it locally. The database remains authoritative for campaign continuity. Keep the conventional API-key provider as a possible future adapter, but do not make its credentials or billing the MVP default.

## Implementation workflow, persistence, and test isolation

- The product owner coordinates parallel coding agents, reviews the user-visible result and behaviour, integrates work, and keeps iterating against this plan. Prefer GPT-6 Sol at high reasoning effort for product-owner work and GPT-6 Luna at xhigh for coding agents when those settings are available; otherwise retain the active settings.
- Run all Erlang, Elixir, Mix, Phoenix, and project test commands in WSL 2 or a Linux VM. Do not use the Windows Elixir installation. Keep PostgreSQL's development data in durable local storage that survives WSL/app restarts; do not use an ephemeral database for the campaign that is played over multiple days. Keep database files, dumps, OAuth tokens, and other secrets out of Git.
- Maintain a fictional, explicitly separate QA campaign for manual feature testing. Never use, overwrite, or import the vineyard campaign for product or regression tests. Automated tests use a separate test database and isolated fixtures. The QA campaign must remain separate from any future approved vineyard import.
- Add a concise `docs/FEATURE_LOG.md` entry for each user-visible feature or meaningful behaviour change, including how it was checked. Update this plan when product decisions or architecture constraints change. Do not create a README yet, per the owner's repository preference.
- The owner authorizes commits directly to `main` and pushes to GitHub until the MVP is workable and polished. The product owner reviews agent changes, focused behavioral tests, and documentation before integrating and pushing each coherent iteration.

## Risks and decisions to track

- **Account access:** The chosen OAuth route is a preview for eligible open-source, locally hosted apps. The user's Plus allowance is shared with other apps and can stop GM requests at a usage limit; the app must pause cleanly and must not switch to billed API calls. Remote hosting requires a separate eligibility process. Conventional API-key usage is a future option only if the owner changes the budget.
- **Legacy history:** The original chat is accessible read-only, but long retrieved messages may be truncated. Review the whole timeline and obtain an authoritative export or owner-approved summary before importing private campaign state.
- **Model fallibility:** A structured or constrained response reduces parsing ambiguity but does not guarantee correct fiction or arithmetic. Validate changes, keep the canonical state in the application, and preserve a reviewable event record.
- **Continuity drift:** LLM-generated summaries can omit, merge, or contradict details. Stable item, location, character, and relationship records plus event-linked state deltas are required before relying on the product for a long-running campaign.
- **Session meaning:** This plan treats a session as a segment inside a campaign. Confirm that model during the creation-flow review if the owner intends independent branches instead.
